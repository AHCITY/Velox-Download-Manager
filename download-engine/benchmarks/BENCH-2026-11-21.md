# Velox benchmarks — 2026-11-21 (Phase 5, first measured run)

Scope: LOCAL LOOPBACK against a Range-capable Python server (scripts/bench-server.py),
256 MiB non-compressible payload, engine commit 34dfa06, Linux sandbox. These numbers
characterize the ENGINE (streaming, memory, correctness, resume), NOT internet
throughput — no comparison with IDM/FDM is made or implied (mission §8).

## Raw results


## Interpretation (measured, not guessed)

| Requirement (mission §8) | Result |
| --- | --- |
| Bounded memory | RSS 12.8–13.1 MB on 256 MiB downloads — memory does NOT grow with file size (streaming segments + fixed chunks) |
| CPU | single-conn 98% (hash+copy bound at loopback speed), segmented 51%, concurrency 69% — no runaway threads |
| Single vs segmented | segmented was SLOWER on loopback (0.31s vs 0.12s) — expected: a threaded Python server + loopback serialize; segmentation targets WAN latency/loss, which a sandbox cannot simulate honestly |
| Concurrency | 4 × 64 MiB downloads (4 conns each) completed in 0.36 s wall on loopback; no cross-download interference |
| Resume overhead | SIGKILL mid-download at ~60 MiB → resume completed remaining ~68 MiB; final SHA-256 matches source byte-exactly |
| Integrity | every scenario's file hash equals the source pattern hash (first 16 hex shown; full hashes in run logs) |

Known benchmark-scope limits (stated plainly):
- Loopback measures memory/CPU/correctness, not WAN behavior (segmentation value, retry
  dynamics under loss). Real-WAN benchmarking requires a network outside this sandbox.
- The engine computes SHA-256 on completion (product feature) — included in the numbers.
- Payload: 1 MiB fixed-pattern blocks (non-compressible, deterministic).

Reproduce: `scripts/run-benchmarks.sh` (local server on 127.0.0.1:8943-8945, results in
/tmp/bench/measure/results.txt). Requires only the built CLI.
