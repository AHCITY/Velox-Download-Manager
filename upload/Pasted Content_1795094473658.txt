# PROJECT: NEXT-GENERATION OPEN-SOURCE DOWNLOAD ENGINE
## Master Engineering & Implementation Directive

You are the lead systems architect, senior Rust engineer, networking engineer, storage engineer, and reliability engineer responsible for building a serious next-generation open-source download manager.

Your task is NOT to create another basic IDM clone.

Your task is to research, architect, implement, test, and continuously improve a high-performance, highly compatible, exceptionally reliable, cross-platform download engine.

The project should eventually compete with and surpass traditional download managers such as Internet Download Manager (IDM), Free Download Manager (FDM), aria2, AB Download Manager, Gopeed, and other established projects.

The most important instruction:

**BUILD THE DOWNLOAD ENGINE FIRST. THE USER INTERFACE IS THE LAST PRIORITY.**

Do not spend substantial development time designing a beautiful interface while the underlying engine is incomplete.

---

# 1. CORE PROJECT VISION

Create an independent download engine that can power multiple applications.

The same underlying engine should eventually support:

- Windows
- Linux
- macOS
- Android
- Potentially other platforms where the required networking and storage capabilities are available.

The engine must be independent of any particular graphical framework.

A desktop application, Android application, command-line client, browser extension, remote web interface, or headless server should all be capable of communicating with the same core.

The architecture must make this possible without duplicating the actual downloading implementation.

Think of the engine as a standalone product with clients, not a desktop application with downloading code embedded inside it.

## Primary objectives (in priority order)

1. Reliability and data integrity.
2. Maximum practical download performance.
3. Exceptional HTTP/HTTPS compatibility.
4. Robust pause, resume, and recovery.
5. Intelligent connection and segment management.
6. Efficient memory, CPU, and disk utilization.
7. Cross-platform portability.
8. Extensible protocols and networking.
9. Comprehensive observability and diagnostics.
10. Simple interfaces for future clients.

Never sacrifice data integrity for an artificial speed improvement.

Do not promise unlimited speed improvements. Measure real throughput and optimize against controlled benchmarks.

# 4. THE DOWNLOAD ENGINE

This is the heart of the entire project.

## A. Intelligent HTTP/HTTPS resource inspection

Before downloading, inspect the remote resource when appropriate.

Determine:

- Final resolved URL.
- Redirect chain.
- HTTP status.
- Content length, if known.
- Range request support.
- ETag.
- Last-Modified.
- Content-Disposition filename.
- MIME type.
- Content-Encoding.
- Authentication requirements.
- Relevant response headers.
- Server behavior.
- Potential connection restrictions.

Use HEAD where useful, but never assume HEAD works or accurately represents GET behavior.

Implement a safe GET-based inspection fallback.

Avoid downloading the entire file just to discover its metadata.

Support:

- Redirects.
- Cookies.
- Custom headers.
- Referer.
- User-Agent.
- Authentication.
- Proxy configuration.
- IPv4 and IPv6.
- TLS verification.
- Unknown file sizes.
- Chunked transfer.
- Servers with incomplete or inconsistent headers.

Do not bypass server restrictions, authentication, access controls, or DRM.

## B. Intelligent segmented downloading

Implement an advanced segmented HTTP downloader.

Requirements:

1. Detect whether the server supports byte ranges.
2. Confirm the resource has a known and consistent representation length.
3. Establish whether multiple connections are actually beneficial.
4. Divide the resource into byte ranges.
5. Download ranges concurrently.
6. Write data into the correct file offsets.
7. Maintain independent progress for every segment.
8. Retry failed segments independently.
9. Reallocate unfinished work.
10. Detect slow or stalled connections.
11. Avoid creating excessive connections.
12. Fall back to single-stream downloading when appropriate.

Investigate IDM-style dynamic segmentation.

Implement a scheduler that can intelligently redistribute unfinished ranges when workers finish early or become disproportionately slow.

Consider:

- Adaptive segment sizing.
- Segment splitting.
- Work stealing.
- Per-host connection limits.
- Minimum segment sizes.
- Maximum connection limits.
- Small-file optimizations.
- Server-specific concurrency adaptation.
- Throughput measurement.
- Connection establishment overhead.
- Latency-aware scheduling.

Do not blindly use 16, 32, or 64 connections for every download.

The engine should determine when concurrency helps and when it hurts.

## C. Universal compatibility fallback

This is non-negotiable.

A modern downloader must not fail simply because a server does not support ideal downloading behavior.

Support these modes:

1. Multi-connection range downloads.
2. Single-connection streaming.
3. Unknown-length streaming.
4. Non-resumable streaming.
5. Resumable single-connection downloads when supported.
6. Servers that reject HEAD.
7. Servers that reject multiple connections.
8. Servers that return unexpected but valid response behavior.
9. Servers with expiring authenticated URLs.
10. Servers with inconsistent or missing metadata.

The engine must distinguish:

- Resumable.
- Conditionally resumable.
- Non-resumable.
- Currently unknown.

Never claim that every download can resume.

When a server cannot resume, explain why and preserve the safest possible behavior.

## D. Persistent resume and recovery

Build a robust recovery subsystem.

It must survive:

- Application crashes.
- Process termination.
- Windows restarts.
- Linux restarts.
- Android process death.
- Unexpected power loss.
- Network disconnections.
- Network interface changes.
- Temporary storage failures.
- Interrupted writes.

Maintain persistent information for:

- Download ID.
- Original URL.
- Resolved URL.
- Destination.
- Expected file size.
- ETag.
- Last-Modified.
- Resource identity.
- Segment boundaries.
- Completed ranges.
- In-progress ranges.
- Verified ranges.
- Retry counters.
- Connection metadata.
- Download configuration.
- Error history.
- Last known state.

Use transactional state updates.

Design crash-safe file writing and recovery rules.

On resume:

1. Inspect the resource again when necessary.
2. Validate resource identity.
3. Check available validators.
4. Detect changed content.
5. Validate the local partial file.
6. Reconcile persistent state with actual file contents.
7. Resume only trustworthy ranges.
8. Restart safely when consistency cannot be established.

A matching filename or matching file size is not proof that the remote resource is unchanged.

Use strong validators where available.

Do not silently combine bytes from different versions of a resource.

## E. Retry and failure management

Create a structured failure classification system.

Handle:

- DNS failures.
- TLS failures.
- Connection timeouts.
- Connection resets.
- HTTP 403.
- HTTP 404.
- HTTP 408.
- HTTP 416.
- HTTP 429.
- HTTP 500.
- HTTP 502.
- HTTP 503.
- HTTP 504.
- Disk-full errors.
- Permission errors.
- File-lock errors.
- Invalid range responses.
- Expired authentication.
- Interrupted downloads.

Use exponential backoff with jitter where appropriate.

Respect Retry-After.

Avoid infinite retry loops.

Separate permanent errors from temporary errors.

Do not retry an entire multi-gigabyte file when only one unfinished segment needs recovery.

Provide configurable policies with sensible automatic defaults.

## F. Storage subsystem

Develop storage independently of the network engine.

Requirements:

- Large-file support.
- Correct random-access writes.
- Segment-to-offset mapping.
- Bounded memory usage.
- Efficient buffered writing.
- Disk-space monitoring.
- Optional file preallocation.
- Temporary file management.
- Safe finalization.
- Atomic completion where supported.
- Collision-safe naming.
- Cross-volume handling.
- File locking.
- Crash recovery.

Consider platform differences instead of assuming every filesystem has identical semantics.

Never expose an incomplete file as successfully completed.

Never mark a segment complete before its data has been safely accounted for according to the documented durability policy.

## G. Integrity verification

Implement:

- SHA-256.
- BLAKE3.
- Trusted externally provided checksums.
- Metalink checksums.
- Whole-file verification.
- Chunk verification when trusted chunk hashes exist.
- Optional post-download verification.
- Duplicate detection.

A locally calculated checksum proves consistency of the downloaded bytes, not authenticity of the source.

Clearly distinguish integrity verification from authenticity verification.

- VPN interfaces.
- Proxy configurations.

- Latency measurement.

Do not make the core HTTP engine depend directly on Windows-specific network APIs.

Use platform adapters.

## Multiple network modes

Implement these as distinct capabilities:

MODE 1 — Normal routing

Use the operating system's normal network routing.

MODE 2 — Interface selection

Allow the user to select a network interface when the platform supports binding connections to it.

MODE 3 — Connection distribution

Allow different downloads or independent HTTP connections to use different interfaces when safe and supported.

MODE 4 — Automatic failover

When an interface becomes unavailable, recover affected connections and resume unfinished work over another available interface.

MODE 5 — True bandwidth bonding

Research bonding through a compatible remote endpoint, VPN, or relay.

Do not misrepresent ordinary connection distribution as true bandwidth bonding.

True bonding requires coordinated infrastructure capable of combining traffic from multiple paths.

## Android USB tethering

Eventually detect USB tethering as an additional network interface.

Do not require invasive phone access.

Use ordinary Android USB tethering where available.

Provide platform-specific capability detection.

Account for Android permissions, background restrictions, battery restrictions, and operating-system limitations.

The first implementation can focus on Windows interface detection and failover, followed by Linux and Android-specific adapters.

# 10. SECURITY AND ROBUSTNESS

Treat URLs, response headers, filenames, cookies, remote metadata, and imported manifests as untrusted input.

Implement:

- Strict TLS certificate verification.
- Safe redirect handling.
- Header validation.
- Filename sanitization.
- Path traversal protection.
- Resource limits.
- Safe cookie storage.
- Credential protection.
- Secure local API authentication.
- IPC access controls.
- Database protection.
- Plugin isolation where plugins are introduced.
- Dependency auditing.

Be especially careful about local-network and loopback URL access.

A downloader that accepts arbitrary URLs can accidentally become an SSRF or local-resource access vulnerability when exposed through a remote API.

Make remote control opt-in and properly authenticated.

Never expose an unauthenticated download-control service to the public internet.

Do not disable TLS verification as a normal compatibility workaround.

Do not silently downgrade security to make a download work.

## FINAL ENGINEERING STANDARD

The result should not merely be a downloader that works under ideal conditions.

It should be a downloader that behaves intelligently under imperfect conditions.

It should handle unreliable internet connections, incompatible servers, changing networks, interrupted processes, large files, disk limitations, and unexpected failures without silently corrupting data.

It should be fast when the server and network allow it, conservative when they do not, and transparent when something goes wrong.

**Build the engine as an independent, reusable, cross-platform systems component. Make reliability its foundation, performance its strength, compatibility its priority, and the graphical interface its eventual client.**

Begin with research, architecture, and a working implementation. Do not stop at recommendations.
